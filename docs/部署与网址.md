# 部署与网址

## 目前的结构

GitHub 仓库：<https://github.com/yelidifei/supervisioncircle>

运行环境：Sites 托管 React 页面与服务端接口，D1 保存小组和每月投票。入口需要设置为公开，导师才能免登录；进入具体小组仍需要完整的共享链接。

本仓库不放实际共享链接或管理链接，以免把参与权限或管理权限公开给仓库访客。请从管理页面复制共享链接。

## 如何让网址不含平台账号名

页面显示名称是 **Supervision Circle**，代码包名称是 `supervisioncircle`。这些名称不会决定托管域名。

Sites 可以修改网站网址的前缀；平台自动附加的账号域名与前缀是两部分。现有 Sites 工具支持绑定自定义域名，但没有修改账号域名的接口。

如果已有自己控制的域名，可以给同一个 Sites 项目绑定一个子域名，按平台返回的记录配置 DNS，并等待域名与 HTTPS 验证成功。保持同一 Sites 项目和 D1，通常无需搬迁投票数据。验证后从新域名进入管理页，重新复制共享链接；完整路径与链接片段需要保留。

更换域名会改变浏览器存储的来源，因此旧域名下记住的姓名或管理入口不会自动迁移。先保存完整管理链接，再进入新地址。

## 如果没有域名

可以部署到自己账号下的 Cloudflare Workers，并使用其提供的地址。仓库已提供独立 Cloudflare 构建模式和配置模板。仍需要登录自己的 Cloudflare 账号、创建 D1、迁移已有数据并验证；仓库上传完成不表示新网站已经上线。[Cloudflare 的 workers.dev 地址说明](https://developers.cloudflare.com/workers/configuration/routing/workers-dev/)。

GitHub Pages 只能托管静态部分，无法直接运行本项目的 D1 服务端接口，因此不能单独替代当前托管。网址缩短服务也不解决实际页面地址中出现平台账号名的问题。

在新的干净地址验证成功之前，不应把旧平台域名当作已满足命名要求的最终共享链接。

## Cloudflare 首次部署

先完成仓库首页的本地安装。然后登录：

```sh
pnpm exec wrangler login
pnpm exec wrangler d1 create supervisioncircle
```

登录时在浏览器中检查并完成授权。创建数据库后，复制 `wrangler.cloudflare.example.json` 为 `wrangler.cloudflare.json`，将 `database_id` 替换为实际返回的 D1 ID。这个本地配置被 Git 忽略。

```sh
pnpm exec wrangler d1 migrations apply DB --remote --config wrangler.cloudflare.json
pnpm deploy:cloudflare
```

只有以上步骤成功后，才使用 Cloudflare 返回的实际网址。Workers 页面可设置自己账号的地址前缀；选择不含不希望出现的账号名的值，并检查最终地址。本版独立 Cloudflare 构建会关闭 Sites 平台插件，页面和 API 在同一个新域名下运行。

此过程新建的是空数据库。迁移现有小组时，部署完成仍不能直接宣布迁移成功：需要保留原表的 `id`、两个密钥摘要、`payload`、`revision` 和 `created_at`，在最后一次同步期间暂停旧站写入，导入新 D1，再比对每位成员、每月候选、回复和最终状态。管理和共享链接只替换网址来源，保留路径与片段。未经比对不要切换日常使用入口，也不要删除旧站数据。

## Cloudflare 后续更新

代码修改后运行常规检查，再执行 `pnpm deploy:cloudflare`。此命令会先进行 Cloudflare 模式的构建，构建失败会停止发布。`pnpm build` 是 Sites 模式，两种模式共用 `dist` 目录。有新增数据库迁移时，在发布前应用增量迁移。

GitHub 推送仍不会自动触发这个手动部署流程；需要自动部署时，可后续配置 Cloudflare 的 GitHub 集成，并限定到本仓库。
